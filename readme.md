# Анализ вариабельности сердечного ритма (HRV)

Скрипт [hrv_analysis.py](hrv/hrv_analysis.py) обрабатывает ряды чисел (интервалы между ударами сердца, мс) 
для нескольких испытуемых и печатает результаты. 
Глубоко в принципы анализа и процесса обработки не погружалась, так как основное задание было именно провести рефактринг и оптимизацию кода.

## Как запускать

Все команды выполняются из корня проекта.

```bash
uv sync
uv run python hrv/hrv_analysis.py
```
### Запуск с помощью контейнера
При успешном окончании запуска через контейнера в stdout будет выведена сводная статистика по всем анализируемым испытуемым.

```bash
docker build -t hrv-analysis:local . # сборка контейнера с заданным назнванием
TEMP_DOCKER_DIR="$(mktemp -d)" # создаем временную директорию для выходных файлов
# запускаем контейнер
docker run --rm \
  --mount "type=bind,source=$TEMP_DOCKER_DIR,target=/app/output" \
  hrv-analysis:local
```

Скрипт создаёт каталог `output/` и записывает туда сводную таблицу и шесть PNG для каждой обработанной записи. Имена входных файлов перечислены в `hrv/analysis/pipeline.py` в переменной `SUBJECTS`. В учебном наборе четвёртый CSV отсутствует, поэтому в журнале появится предупреждение о его пропуске.

Проверить результат можно из корня:

```bash
uv run ruff check . # проверка пайплайна
uv run ruff format --check . # проверка форматирования
uv run mypy hrv # проверка типов
uv run pytest # запуск тестов
```

### Журнал запуска

После реализации принципа логирования с помощью `logger` показатели испытуемых и сводная таблица выводятся в stdout, а служебные сообщения идут в stderr. Их можно сохранить в отдельный файл лога с помощью следующей команды:

```bash
uv run python hrv/hrv_analysis.py 2>hrv.log
```

**Важно**: не перенаправлять все и stderr, и stdout в файл лога, потому что иначе туда войдет и сводная статистика по запуску анализа против данных.

В логировании сейчас реализованы следующие уровни обхода:

| Уровень | Когда появляется | Результат |
|---|---|---|
| INFO | Начинается чтение записи или успешно завершена запись сводной CSV | В журнале видны путь и число строк сохранённой сводки |
| WARNING | Файл отсутствует, не читается или содержит слишком мало пригодных интервалов | В журнале указываются путь и причина, обработка переходит к следующей записи |
| CRITICAL | Ошибка ввода-вывода прервала запуск, например при создании каталога, сохранении PNG или CSV | Сообщение в stderr и код завершения 1 |

### Совместимость с контролем

В учебном алгоритме мода для индекса напряжения фиксирована (975 мс), а размах равен суммарной ширине занятых столбцов гистограммы. Частота FFT выражена в циклах на интервал. Точка 0.015 входит одновременно в диапазоны ULF и VLF. Вызовы `nolds` явно задают линейную аппроксимацию, которую использует исходный скрипт с зависимостями проекта.

### Fixed bugs

- Скрипт сам создаёт каталог результатов при первом запуске.
- Файл с нечисловыми данными или менее чем двумя интервалами после очистки пропускается с соответствующим сообщением. При этом обработка остальных записей продолжается.
- Для коротких записей графики используют доступные сдвиги и пары соседних интервалов, а не фиксированные переменные. Неопределённые отношения и корреляции обозначаются `nan` в консоли, в то время как числовые пропуски в сводной CSV остаются пустыми.
- Для постоянных рядов и записей короче десяти очищенных интервалов показатели Херста и DFA получают значение `nan`.
- Добавлены обход ошибок разного формата и вывод соответствующих неисрпавлностей, предупреждений с помощью логирования в stderr
- Добавлен Dockerfile для запуска пайплайна из-под контейнера - позволяет пользователям избегать проблем с созданием окружения ввиду конфликтов зависимостей с их текущей операционной системой, версиями пакетов и т.д.
- Реализовано unit-тестирование и подготовлены ожидаемые unit-тестовые данные
- Добавлен .gitignore файл для "чистки" от выходных файлов и файлов запуска, создания окружения

## Производительность

Для оценки производительности я подготовила тестовые данные (не для unit-тестирования из директории  `tests`) с помощью случайной генерации значений интервалов (попросила нейронку подготовить скрипт для генерации, указывая точные диапазоны, параметры и типы значений, файлов). Сравнивала производительность исходного скрипта из `dc20268` и рабочий оптимизированный вариант из ветки `refactor/06-cleanup` на базе `be05fa0`. В каждом запуске обрабатывался один синтетический CSV. Время включает запуск нового процесса Python, импорты, чтение файла, фильтрацию, расчёт всех метрик, сохранение шести PNG и сводной CSV.

| Интервалов на запись | Исходный скрипт, с | После рефакторинга, с | Исходный скрипт, пик RSS, МиБ | После рефакторинга, пик RSS, МиБ |
|---:|---:|---:|---:|---:|
| 1 000 | 1,276 | 1,273 | 241,4 | 234,9 |
| 10 000 | 2,178 | 2,107 | 343,0 | 352,0 |
| 50 000 | 6,141 | 5,552 | 706,5 | 724,2 |

Для каждого объёма приведены медианы трёх запусков по времени и пиковому RSS процесса. Перед измерениями обе версии прошли один тестовый запуск на 330 интервалах. Порядок запуска версий чередовался. Среда — macOS 26.4.1, arm64, Python 3.13.9, NumPy 2.5.5, SciPy 1.18.1, nolds 0.6.3, pandas 3.1.1, Matplotlib 3.11.2 с backend Agg. Переменные числа потоков BLAS и OpenMP были выставлены за 1.

Если подробнее, то входные данные для каждого объема интервалов были получены с помощью `np.random.default_rng(42).integers(780, 861, size=n)` и записаны в `subject_01.csv` по одному числу на строку. В данном случае все интервалы проходили фильтрацию. Сама при этом генерация тестовых данных в оценку производительности не включалась. На каждом прогоне я проверяла шесть PNG, строку испытуемого в таблице и совпадение итоговой CSV у обеих версий.

Касательно обработки объемныъ данных текущая реализация после рефакторинга все еще, как мне кажется, не самая оптимизированная. На 50 000 интервалах медианное время уменьшается на 9,6%, а медиана пикового потребления памяти вырастает на 17,7 Мб. И важным ограничением является то, что сейчас автокорреляция рассчитывается только для используемых сдвигов от 0 до 128, то есть заведомо сокращается возможное количество. В отдельном запуске под `cProfile` на том же входе расчёт DFA занял уже 4,03 с из 7,74 с, а отрисовка путей с помощью Matplotlib (`draw_path`) — 1,86 с. Время запуска под профилировщиком учитывалось отдельно и не включалось в итоговую таблицу производительности.

Важно заметить, что скрипт оценки производительности обрабатывает CSV целиком и создаёт массивы для фильтрации, спектра и построения графиков. И сейчас перформанс оценивался только на максимальном количестве записей равном 50 000 интервалам. Тестирование на реальных, объемных данных большого набора испытуемых и также на данных с большим числом выбросов я не проводила принципиально из-за оагрничений по времени и дополнительных параллельных отчетностей, перевода статей, диссертационного проетка. Понимаю, что это не аргумент, но так как у меня и недостаточно квалификации в данном направлении, то я еще боялась, что не смогу отобрать корректные наборы данных.
